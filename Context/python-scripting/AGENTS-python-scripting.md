# NodeToCode Python Scripting

The stdio MCP bridge, the `nodetocode` Python module and run-python for LLM-powered UE automation. NodeToCode 2.0
has no script library (decision 0010, card 0305): the six saved-script tools and `script_registry.json` are gone;
reusable scripts belong in Agent Skills (`Context/agent-skills/AGENTS-agent-skills.md`).

## MCP Bridge

### nodetocode_bridge.py

Stdio-to-HTTP bridge enabling MCP clients (Claude Desktop, etc.) to communicate with NodeToCode's MCP server.

*   **Location**: `Content/Python/mcp_bridge/nodetocode_bridge.py`
*   **Purpose**: Forward JSON-RPC messages between MCP clients and UE5
*   **Key Features**:
    *   stdin and stdout are reconfigured to UTF-8 (the launchers also set `PYTHONUTF8=1`), so non-ASCII text is
        not decoded with the Windows ANSI code page
    *   Each stdin message is POSTed to `/mcp` with `Accept: application/json, text/event-stream`.
        A `text/event-stream` response (UE 5.8's streamed `translate-focused-blueprint`) is parsed per the SSE spec
        and each message in it is written to stdout as it arrives; the response to the request ends the call
    *   One thread reads stdin (`Bridge.submit`); every request except `initialize` runs on its own worker thread,
        so `ping` and a quick tool answer while a translation runs. `initialize` and notifications go in order on
        the reader thread; stdout writes are serialized under a lock
    *   `notifications/cancelled` is forwarded at once (and once more a second later if the call still runs, in
        case it overtook its request); from then on nothing is written for that request id (the editor sends no
        response, and the bridge's own "stream ended" error is dropped). A request cancelled before it was sent is
        never sent
    *   stdout carries only JSON-RPC messages, one per line: a transport failure or non-JSON body (an HTTP error
        page) becomes a JSON-RPC error with the request's id, and notifications never get a reply
    *   Editor selection (`EditorLocator`): `--url` or `--port` names the editor. Otherwise it reads the discovery
        entries the editor's MCP server writes (card 0112: `<UserSettingsDir>/NodeToCode/servers/<pid>.json`, that
        is `%LOCALAPPDATA%` on Windows, `~/Library/Application Support/Epic` on macOS, `~/.config/Epic` on Linux;
        plus `<Project>/Saved/NodeToCode/mcp-server.json` when `--project` is a path), skipping entries whose pid is
        gone. One editor: that one. `--project` / `NODETOCODE_PROJECT` matches the project name, `.uproject` path or
        folder; several editors and no selection is a JSON-RPC error listing them (`error.data.editors`).
        `NODETOCODE_DISCOVERY_DIR` replaces the index folder (tests). An entry is used only when `loopback_url` accepts
        its `url` (card 0426): scheme http, host in 127.0.0.0/8, `localhost` or `::1` (IPv4-mapped loopback too), no
        user info, a valid port; host names are never resolved. The entry's `url` is replaced by the URL rebuilt from
        those parts; any other entry is logged to stderr and skipped. `--url`/`--port`/`--host` are not checked.
        Tests: `Tests/python/test_mcp_bridge_discovery.py`
    *   Lazy connect: the bridge starts without an editor and looks again on every request; until one answers, each
        request gets a JSON-RPC error with its id. When a discovered editor refuses the connection, the bridge looks
        again and, if the entries now name another editor, replays the client's `initialize` there and resends
    *   Session management with `Mcp-Session-Id` (and `MCP-Protocol-Version` after initialize); a 404 replays
        `initialize` and resends once; stdin EOF waits for calls in flight, then sends DELETE
    *   MCP 2026-07-28 (card 0210): a message whose `params._meta` has `io.modelcontextprotocol/protocolVersion` is
        sent without a session, with `MCP-Protocol-Version`, `Mcp-Method` and `Mcp-Name` (`modern_headers`; Base64
        sentinel when the name is not plain ASCII). Its `notifications/cancelled` closes the request's HTTP stream
        (`close_response`) instead of being forwarded, which is how 2026-07-28 cancels over HTTP. Tests:
        `Tests/python/test_mcp_bridge_modern.py`
    *   No read timeout by default (a held translation sends nothing until it finishes); `--timeout SECONDS` sets one
    *   Bearer token (card 0183): `TokenSource` sends `Authorization: Bearer <token>` on every request (initialize
        replays and DELETE too) from `--token-file`, else `NODETOCODE_MCP_TOKEN`, else the editor's per-user
        `<UserSettingsDir>/NodeToCode/mcp-token`, read again for each request so a regenerated token is used at once; no
        token, no header. A 401 is logged with where the token came from (never the token) and returned as the
        JSON-RPC error with the request's id. Tests: `Tests/python/test_mcp_bridge_token.py`
    *   Debug mode with `--debug` flag (logs go to stderr)
*   **Usage**:
    ```bash
    python nodetocode_bridge.py [--project NAME_OR_PATH] [--port PORT [--host HOST]] [--url URL] [--token-file PATH] [--timeout SECONDS] [--debug]
    ```
*   **Tests**: `python -I -m unittest discover -s Content/Python/tests -p "test_mcp_bridge*.py"` (no editor; fake
    editors on http.server and fake discovery folders); live: `Tests/mcp_probe/live_stdio_bridge.py` and
    `Tests/mcp_probe/live_bridge_concurrency.py`

### launch_bridge.bat (Windows) and launch_bridge.sh (Mac/Linux)

Launchers that pick the Python through `ue_python_finder.py`:

1. Run `ue_python_finder.py` with `py -3`, `python3` or `python` (the `.sh`: `python3`, then `python`); it prints
   the bundled Python of the newest UE install it finds, else the Python that ran it
2. Without a Python on PATH, the bundled Python of a registered launcher install (Windows registry, any version) or
   of a `UE_*` folder in a common install folder (`.sh`) runs the finder
3. Set `PYTHONUTF8=1` and pass all arguments to the bridge script

### ue_python_finder.py

Python installation finder using the same methods as UnrealVersionSelector:

*   **Windows Registry**: `HKEY_CURRENT_USER\SOFTWARE\Epic Games\Unreal Engine\Builds`
*   **Epic Games Launcher**: `LauncherInstalled.dat` file
*   **Common paths**: every `UE_*` folder in standard UE installation directories (no fixed version list)
*   Installs are ordered by the version in their `Engine/Build/Build.version`; `--list` prints them all
*   **Functions**:
    *   `find_ue_python(prefer_newest=True)` - Find UE's bundled Python
    *   `find_ue_source(prefer_newest=True)` - Find Engine/Source path
    *   `find_python(prefer_ue=True)` - Find any Python, preferring UE's

## NodeToCode Python Module

Importable module providing Blueprint manipulation. All functions return standardized dictionaries with `success`, `data`, and `error` keys.

### Quick Start

```python
import nodetocode as n2c

# Blueprint operations (a Blueprint graph must be focused: open one with n2c.open_blueprint(path))
bp = n2c.get_focused_blueprint()
if bp['success']:
    print(f"Blueprint: {bp['data']['name']}, graph {bp['data']['graph_name']}, {bp['data']['node_count']} nodes")

n2c.compile_blueprint()
n2c.save_blueprint()

# Tagging system
n2c.tag_graph("player_controller", category="Systems")
tags = n2c.list_tags()
```

### Module Files

| File | Purpose |
|------|---------|
| `__init__.py` | Module exports (`__all__`), version info (`__version__ = "1.0.0"`) |
| `blueprint.py` | Blueprint get/read/load via `UN2CPythonBridge`; compile and save through the MCP tools (`invoke_tool`) |
| `graph.py` | Graph editing through the MCP tools (`invoke_tool`): node search, add, connect, pin values, delete, find, comments |
| `functions.py` | Function input and return pins through the MCP pin tools (`invoke_tool`) |
| `bridge.py` | Tagging, LLM provider info, `open_blueprint` and `open_blueprint_function` |
| `utils.py` | Logging (`log_info`, `log_warning`, `log_error`), result helpers, `_parse_bridge_result`, `invoke_tool`, `_invoke` with `TOOL_NAMES` and `BRIDGE_ONLY`, `LegacyKeys` |

### Tools from Python: invoke_tool (card 0342)

`UN2CPythonBridge::InvokeTool(ToolName, ArgumentsJson)` runs any registered MCP tool through the tool catalog
(`FN2CToolCatalog::InvokeNow`) and returns `{success, data, error}` (`code` and `field` on a failure: `UNKNOWN_TOOL`,
`INVALID_ARGUMENT`, `PIE_ACTIVE`, `NOT_RUNNABLE_HERE`, `TOOL_FAILED`). It resolves from a private tool manager
configured with every toolset except PythonTools, so it reaches tools the MCP server does not serve (the Python
Scripting profile serves only run-python); run-python is refused, and a
long-running tool (translation) gets `NOT_RUNNABLE_HERE`. It runs inline on the game thread, inside a run-python call
too (the outer tool call compiles once). `data` is the tool's value: its JSON object or array, else its text.

`nodetocode.invoke_tool(name, arguments)` is the Python form. The 17 functions in `utils.TOOL_NAMES` (search, add,
connect, set pin, delete, find, comment, the four function-pin calls, compile, save, `tag_graph`, `open_blueprint`,
`open_blueprint_function`, `get_blueprint_dependencies`) run their tool through `utils._invoke`, so they behave exactly as the MCP tools
(`NodeToCode.Python.ToolParity` compares each with tools/call). Their `data` is the tool's result plus, for one
release, the keys the 1.x bridge copies returned (`LegacyKeys`: reading one with `[]` or `get()` logs one deprecation
warning naming the tool's key; the tool's own key wins where both exist, e.g. a pin's `type` is `String`). A tool
value with `"success": false` (compile errors) makes the result a failure with the tool's `message` as `error`.
`utils.BRIDGE_ONLY` lists the functions still on their own bridge UFUNCTION and why: `get_focused_blueprint` (the
tool's N2C JSON uses `ids` objects), `list_tags` and `remove_tag` (the tag tools take no Blueprint path, card 0498),
`get_llm_providers` (the tool lists configured providers only). The UFUNCTIONs themselves stay until card 0343 turns
them into forwarders.

### Available Functions

The authoritative list is `__all__` in `Content/Python/nodetocode/__init__.py`; each function's docstring gives its
arguments and the keys of its `data`. Grouped:

**Blueprint Operations:**
*   `get_focused_blueprint()` - The focused graph as N2C JSON: `data` has `name`, `path`, `graph_name`, `node_count`
    and `n2c_json` (version 2.0.0, stable names: each node's `class`, `member_parent`, `member_name`, each pin's
    `name` such as `execute`, `then` or `ReturnValue`; `title` and `label` are English display hints). Like the MCP
    `get-focused-blueprint` tool it keeps the editor's unwired default events (a new Actor Blueprint's greyed-out
    BeginPlay, ActorBeginOverlap and Tick) as `"disabled": true` nodes, so a script finds the default BeginPlay and
    wires it instead of adding a second one: a new Actor Blueprint's untouched EventGraph gives `node_count` 3 and
    those three nodes (card 0433). Translation leaves them out, and translating a graph of only those events fails
    with "Nothing to capture: the graph holds only unwired default events (ghost nodes)"
*   `get_blueprint_n2cjson(blueprint_path, graph_name='', graph_guid='', depth=-1, to_file=False, compact=True)` -
    Any Blueprint's graphs by asset path, with no editor open (`UN2CPythonBridge::GetBlueprintN2CJson`, card 0157):
    `data` has `blueprintPath`, `blueprintName`, `graphCount`, `nodeCount`, `estimatedTokens`, `target` (when a graph
    was named) and `n2c_json`, the document the MCP get-blueprint-n2cjson tool returns; every graph when no graph is
    named. There is no size limit here: `to_file=True` writes the document under `Saved/NodeToCode/Exports` and
    returns `path` and `bytes` instead. Errors start with a code (`ASSET_NOT_FOUND`, `GRAPH_NOT_FOUND`, `EMPTY_GRAPH`,
    `UNSUPPORTED_GRAPH_TYPE`)
*   `list_blueprint_graphs(blueprint_path)` - Every graph of a Blueprint by asset path, as list-blueprint-graphs
    returns it (`UN2CPythonBridge::ListBlueprintGraphs`): `graphs` with `name`, `graphGuid`, `kind`, `nodeCount`,
    `readOnly` and, for collapsed graphs, `parentGraph`
*   `get_blueprint_dependencies(paths, include_call_graph=True, include_referenced=True, to_file=False)` - The
    dependency index under asset paths or content folders (a string or a list), as get-blueprint-dependencies returns
    it but always whole (the tool through `invoke_tool`, card 0319/0342: an index over the tool's inline limit gets its
    lists back from the export, `savedTo`; at most 100 paths): `nodes`, `edges`, `order` (dependencies first),
    `cycleGroups`, `warnings`; with `to_file` also `savedTo` (`Saved/NodeToCode/Dependencies`)
*   `read_n2c_json(text)` - Read N2C JSON 1.x or 2.x (for example a saved `N2C_BP_*.json`) with the plugin's reader
    (`UN2CPythonBridge::ReadN2CJson`); returns its source version, counts (`data_edges`, `exec_edges`) and the document
    as current (2.0.0) N2C JSON; exec flows are "N1.P2->N3.P4" pin pairs, and a 1.x file keeps its "N1->N2" node pairs;
    a 1.x node's display `name` comes back as `title` (no `class`), its pin names stay the display names it has.
    A later 2.x document keeps its version, its unknown node, pin, graph and blueprint types and its unknown fields
    (card 0445), each listed in `warnings` (`code`, `path`, `value`, `message`). The `n2c_json` of
    `get_blueprint_n2c_json` reads too: its `ids.short` is the node or pin ID (card 0505). A read that had to skip a
    graph, node or pin (a missing required field) fails: `error` names the skipped parts, `data` holds the rest
*   `compile_blueprint(path=None)` - Compile the Blueprint at `path` (loaded if needed; the focused one is never
    touched), else the focused Blueprint (card 0297); `data` is compile-blueprint's (`blueprintName`,
    `blueprintPath`, `compilationStatus`, `results` with `errorCount`, `warningCount` and `messages`, each `severity`,
    `message`, and `nodeGuid`, `nodeTitle`, `graph`, `pin` when it names a node); compile errors make it a failure.
    The 1.x `blueprint_name`, `blueprint_path`, `status`, `had_errors`, `had_warnings`, `error_count`,
    `warning_count` and `messages` are kept for one release
*   `save_blueprint(path=None, only_if_dirty=True)` - Save the Blueprint at `path`, else the focused Blueprint;
    `data` is save-blueprint's (`message`, `blueprintPath`, `packageInfo`, `sourceControl` when it wrote the file),
    with the 1.x `blueprint_name`, `blueprint_path`, `was_dirty`, `was_saved` for one release
*   `load_blueprint(path)` - Load Blueprint by asset path; `data`: `name`, `path`, `class_name`, `parent_class`
    (the parent's name, such as `Actor`)
*   `open_blueprint(path, focus_graph=None)` - Open a Blueprint editor and focus a graph by name, matched
    case-insensitively (`EventGraph`, `ConstructionScript` or `UserConstructionScript`, a function or macro name).
    Without `focus_graph` it focuses the EventGraph, or none when the Blueprint has no EventGraph. An unknown name
    fails with `GRAPH_NOT_FOUND` listing the Blueprint's graphs and does not open the Blueprint
*   `open_blueprint_function(name)` - Focus a function graph of the open Blueprint

**Graph Editing (a named graph, else the focused one):** every call below, and the function pin calls and
`tag_graph`, also take `blueprint_path=""` and `graph=""` (card 0274): `blueprint_path` names the Blueprint
(`/Game/BP_Door`), `graph` a graph of it by GUID (a function's `functionGuid`) or by name. With neither, the
focused graph as before; with `blueprint_path` alone, its focused graph or else its event graph. No Blueprint editor
needs to be open then. A target that does not resolve fails with the resolver's code (`ASSET_NOT_FOUND`,
`GRAPH_NOT_FOUND`, `AMBIGUOUS_GRAPH_NAME`, `READ_ONLY_GRAPH`, `NO_FOCUSED_GRAPH`).
*   `search_blueprint_nodes(term, context_sensitive=True, max_results=20, category="", exclude_vm_functions=True)` -
    Actions to add, as search-blueprint-nodes returns them: each an N2C JSON node with `spawnMetadata`
    (`actionIdentifier`: the stable spawner-signature ID, card 0277; `nodeName`; `category`). The 1.x keys `menuName`,
    `name`, `displayName`, `category` and `count` are kept for one release; `tooltip` and `keywords` are empty. `category` filters
    on the menu category, ignoring case and spaces. `context_sensitive` True and False search the same list, the
    target graph's (the editor's node menu with Context Sensitive off), and set only `isContextSensitive`; both need
    a graph, named or focused (card 0434)
*   `add_node_to_graph(node_name, action_identifier, location_x=0, location_y=0)` - Add a node (pass a result's
    `spawnMetadata.nodeName` and `spawnMetadata.actionIdentifier`; pre-0277 search-text identifiers still work);
    returns `nodeGuid` and `inputPins`/`outputPins` with `pinGuid`, `pinName`
*   `connect_pins(connections, break_existing_links=False)` - `[{"from": {"nodeGuid", "pinGuid"}, "to": {...}}]`;
    without `break_existing_links` a connection that would replace a link (a linked data input, also through a
    conversion node, or a linked exec output) fails and names that link
*   `set_pin_value(node_guid, pin_guid, value, pin_name="")` - Default value of an unlinked input pin
*   `delete_nodes(node_guids, preserve_connections=False, force=False)` - Delete nodes as the editor does; `preserve_connections` reconnects the exec line through a node with one exec input and output (and reroute knots); GUIDs not deleted are listed under `skipped`
*   `find_nodes_in_graph(search_terms, search_type="keyword", case_sensitive=False, max_results=50)` - A keyword
    matches the node's title (as shown and its source text), class or member name; or `search_type="guid"`. Nodes
    come as N2C JSON (`ids.guid`, `input_pins`/`output_pins` with `ids.guid` and `ids.name`); the 1.x `nodeGuid`,
    `nodeName`, `nodeClass` and `inputPins`/`outputPins` (`pinGuid`, `pinName`) are kept for one release
*   `create_comment_node(node_guids, comment_text="Comment", color=None, font_size=18, move_mode="group", padding=50)`

Pick pins by `pinName` (`execute`, `then`, `ReturnValue`, `InString`, ...): it is the stable pin name, while
`displayName` is the editor's label.

Compiling (card 0151): the edit calls above and the function pin calls below compile the Blueprint once per call,
after the call's undo transaction, and return the compiler's diagnostics in `data.compile` (`success`,
`errorCount`, `warningCount`, `messages` with `nodeGuid` and `graph` when a message names a node). Inside
`run-python` they compile nothing themselves: the run-python tool call compiles each edited Blueprint once when the
script ends and reports it as `compile` in its own result, so a script that adds and wires 30 nodes compiles once.
`create_comment_node` never compiles; searches and finds compile nothing and refresh nothing.

**Function Pins (a function graph, named or focused):**
*   `add_function_input_pin(name, type, default_value="", is_pass_by_reference=False, tooltip="")`,
    `add_function_return_pin(name, type, tooltip="")`, `remove_function_entry_pin(name)`,
    `remove_function_return_pin(name)`
    They run the MCP pin tools' own path (card 0156): return values go on every Return node, the function's call nodes

**NodeToCode-Specific:**
*   `tag_graph(tag, category="Default", description="", blueprint_path="", graph="")` - Tag a graph, else the focused one
*   `list_tags(category=None, tag=None, blueprint_path=None)` - List tags with filters; `blueprint_path` keeps one Blueprint's graphs (a duplicated Blueprint shares its graph GUIDs with the original)
*   `remove_tag(graph_guid, tag, blueprint_path="")` - Remove tag from graph; pass the entry's `blueprint_path` from `list_tags` (needed once a copy of the Blueprint shares the GUID)
*   `get_llm_providers()` - Get available LLM providers
*   `get_active_provider()` - Get current LLM provider info

**Utilities:**
*   `get_editor_subsystem(class)` - Safely get editor subsystem
*   `is_blueprint_valid(obj)` - Check if object is Blueprint
*   `get_project_content_dir()`, `get_project_dir()` - Path helpers
*   `log_info/warning/error(msg)` - Logging to UE output

## Saved scripts from 1.x

1.x kept scripts in `<Project>/Content/Python/scripts/<category>/` with a `script_registry.json`, through the
list/search/get/save/delete-python-script tools and `nodetocode.list_scripts`/`run_script`/`save_script`. 2.0
removes those tools and functions (card 0305) but never touches the project's files. To keep using a script, make it
an Agent Skill: a folder with a `SKILL.md` (frontmatter `name` and `description`, then when and how to use it) and the
script under its `scripts/`; the agent reads the skill and runs the script through `run-python`, or imports it
after adding the folder to `sys.path`. The registry file can be deleted.

## C++ Bridge (UN2CPythonBridge)

Bridge class exposing NodeToCode functionality to Python via `unreal.N2CPythonBridge`:

*   **Location**: `Source/Private/MCP/Python/N2CPythonBridge.h/.cpp`
*   **UFunction Category**: `NodeToCode|Python`
*   **Functions**: every public `UFUNCTION` in the header. `InvokeTool` (`utils.invoke_tool`) runs any MCP tool, and
    the 17 wrappers in `utils.TOOL_NAMES` call it rather than their own UFUNCTION below (card 0342; card 0343 turns
    those into forwarders). The rest have their own `nodetocode` wrapper (call the wrapper, which parses the JSON and
    checks arguments): `GetFocusedBlueprintJson`, `GetBlueprintN2CJson`,
    `ListBlueprintGraphs`, `GetBlueprintDependencies`, `ReadN2CJson`, `CompileFocusedBlueprint`,
    `SaveFocusedBlueprint` (`blueprint.py`); `TagFocusedGraph`, `ListTags`, `RemoveTag`, `GetLLMProviders`,
    `GetActiveProvider`, `OpenBlueprint`, `OpenBlueprintFunction` (`bridge.py`); `SearchBlueprintNodes`,
    `AddNodeToGraph`, `ConnectPins`, `SetPinValue`, `DeleteNodes`, `FindNodesInGraph`, `CreateCommentNode`
    (`graph.py`); `AddFunctionInputPin`, `AddFunctionReturnPin`, `RemoveFunctionEntryPin`, `RemoveFunctionReturnPin`
    (`functions.py`). The header comments become the Python docstrings (`help(unreal.N2CPythonBridge.open_blueprint)`).

All functions return JSON strings in format: `{"success": bool, "data": {...} or null, "error": "..." or null}`,
built by one helper with `TJsonWriter` (`MakeResultJson`), so every value is escaped; `utils._parse_bridge_result`
is the one parser.

## Struct Library (UN2CStructUtilsLibrary)

`unreal.N2CStructUtilsLibrary` (`Source/Public/BlueprintLibraries/N2CStructUtilsLibrary.h`) creates
UserDefinedStruct assets, for example DataTable row structs (the `struct_creator` script that wrapped it was removed
with the script library, card 0305). Its functions report through out parameters, and in Python a function with
out parameters returns a tuple: the return value first (when there is one), then the out parameters in order.

```python
import unreal

lib = unreal.N2CStructUtilsLibrary

# Create a new struct (the return value comes first, then the out parameters)
struct, success, error = lib.create_user_defined_struct('/Game/Data', 'F_MyRowStruct')
if not success:
    raise RuntimeError(error)

# Add variables to the struct; each call returns (success, error)
for name, var_type in [('MyString', 'FString'), ('MyFloat', 'float'), ('MyInt', 'int32')]:
    ok, error = lib.add_struct_variable(struct, name, var_type)
    if not ok:
        raise RuntimeError(error)

# A new struct starts with one default member; remove it once the struct has others, then save
lib.remove_default_variable(struct)
lib.save_struct(struct)
```

`add_struct_variables_batch` returns `(count, success, error)`; `get_struct_variable_names` returns the members'
names as given (`MyFloat`). `add_struct_variable` refuses a name the struct already has and adds nothing.
`remove_default_variable` removes only the bool `MemberVar_<n>` member a new struct starts with, and only once the
struct has another member; on any other struct it returns `(False, error)` and removes nothing.

## run-python

The one MCP Python tool: `run-python` (`FN2CMcpRunPythonTool`, `Source/Private/MCP/Tools/Implementations/Python/`).
It requires Game Thread execution (`RequiresGameThread() = true`) and answers with one text item holding JSON
`{"success", "data", "error", ...}`. When `success` is false (the script raised or did not compile) the
CallToolResult also has `isError: true`, so MCP clients see a tool execution failure; the body then keeps the error,
`traceback`, `output`, `stderr` and a `hint`. Python being unavailable is an `isError` result whose text is a plain
message.

run-python runs through `nodetocode._mcp_runner` (card 0299). C++ sends one statement,
`__import__('nodetocode._mcp_runner', ...).run_code('<call id>', '<base64 source>')`, unattended
(`EPythonCommandFlags::Unattended`, so no modal dialog blocks the call). The runner compiles the code unchanged
(`compile(source, '<run-python>', 'exec')`: tracebacks name the code's own lines, multi-line strings and
`from __future__` work, a `.py` in a comment is just text) and runs it in a fresh namespace, never the editor
console's globals, so a call never sees another call's names or `result`. It captures the code's stdout and stderr
and hands its answer to `UN2CPythonBridge::SubmitMcpResult` as strict JSON; nothing is scraped from stdout, so a
printed line cannot pose as the answer (`N2CMcpPythonRunner`).

run-python returns what the code assigns to `result` as `data`, written as strict JSON: a UObject (anything with
`get_path_name`) as its path name, `unreal.Name` and `unreal.Text` as strings, sets as lists, structs through
`export_text`. NaN, infinity or a value of another type fail the call with `result not JSON-serializable: ...`
naming the problem. Printed text comes back as `output`, and `seconds` says how long the code ran.

Timeout (card 0300): `timeout` (default 60, at most 300) is enforced inside the interpreter. Tool calls run on the
game thread, so nothing can stop the editor from waiting for the script; instead `nodetocode._mcp_runner.Deadline`
starts a watcher thread that, at the deadline, raises `ScriptTimeout` (a `BaseException`, so `except Exception:`
does not swallow it) in the game thread with `PyThreadState_SetAsyncExc`, and again every half second until the
code lets go. CPython delivers it between bytecodes, so Python code (`while True: pass`, a long loop) stops within
milliseconds of the deadline; a native call in progress (an engine function, an asset scan, `time.sleep`) cannot be
interrupted and runs to its end first. The answer is then an `isError` result with `timed_out: true` and an error
starting `timed out:` that gives the time it actually ran. Specs: `NodeToCode.MCP.RunPythonTransaction` (timeout 2
returns within 5 s and the editor ticks again), `NodeToCode.MCP.PythonToolErrors`; pytest `test_mcp_runner.py`.

Undo (card 0300): each call runs inside `FScopedTransaction("MCP: run-python")`, closed before the tool call compiles
what the script edited. Changes that call `Modify()` are recorded: `set_editor_property`, editor subsystems, asset
tools, NodeToCode's own tools. The actors selected in the level and their components are recorded up front with
`Modify(false)`, so a plain setter on them (`set_actor_location`) is undone too, and their level is marked dirty only
when the script moved one. Any other object a plain setter changes is not recorded unless the script calls
`obj.modify()` first. The editor drops a transaction that changed nothing (`FTransaction::IsTransient`), so a
read-only or failing-before-any-edit script adds no undo step. Nothing is rolled back on an error.

## Python-Only Mode

Setting: Project Settings > Plugins > Node to Code > MCP Server > **Tool Profile** = **Python scripting only**
(`UN2CSettings::McpToolProfile = EN2CMcpToolProfile::PythonScripting`, default `DefaultToolsets`; read when the MCP
server starts, so it needs an editor restart). It serves the `PythonTools` toolset only; Tool Exposure still applies
(profiles, toolsets and tool search are described in `Source/Private/MCP/Tools/AGENTS.md`). A config that saved the
former **Enable Python Script-Only Mode** (`bEnablePythonScriptOnlyMode=True`) loads as this profile (card 0165).

When enabled:
*   Only the `PythonTools` toolset is served (`FN2CMcpToolManager::Configure`): `run-python`, the one tool left in it
    since card 0305
*   No translation, LLM provider, Blueprint, Content Browser or file tools: `get-focused-blueprint` and
    `translate-focused-blueprint` answer "Unknown tool"; a script reaches them with `nodetocode.invoke_tool`
*   Without Allow MCP Python Execution (below) nothing is served, and the editor logs a warning at start
*   LLMs write Python via `run-python` instead of using C++ tools, with Context7 MCP for UE Python API documentation

## python-scripting Prompt

MCP prompt (`FN2CMcpPythonScriptingPrompt`) enforcing proper workflow:

*   **Location**: `Source/Public/MCP/Prompts/Implementations/N2CMcpCodeGenerationPrompt.h`
*   **Name**: `python-scripting`
*   **Arguments**: `task` (required) - what the script should accomplish (the 1.x `save_script` and `category`
    arguments went with the script library, card 0305)

**Workflow it asks for:**
1. **Use what exists** - a loaded Agent Skill, a NodeToCode tool (`n2c.invoke_tool`) or the `nodetocode` module
2. **Research UE Python API** - Use Context7 to lookup `radial-hks/unreal-python-stubhub`
3. **Write the script** - functions with docstrings, edits in a `ScopedEditorTransaction`, `result` set
4. **Run and verify it** with run-python
5. **Keep it as an Agent Skill** if it is reusable

**With Python execution off** (the per-user **Allow MCP Python Execution**, default off; card 0124): the prompt checks
`FN2CMcpToolManager::IsToolRegistered("run-python")` and, when it is not registered, opens with a "run-python is
disabled on this server" section naming the setting (Editor Preferences > Plugins > Node to Code (User) > MCP Server,
editor restart), says run-python is unavailable, and tells the agent to give the script to the user to run and not
to claim it ran. Step 4 and the tool list say the same.

## Script Structure Guidelines

Scripts (a skill's `scripts/` file, or code sent to run-python) follow this pattern:

```python
"""
Brief description of what the script does.

Functions return standardized dicts: {success: bool, data: {...}, error: str|None}
"""

import unreal
from typing import Dict, Any

from nodetocode.utils import make_success_result, make_error_result, log_error


def main_function(arg1: str, arg2: int = 10) -> Dict[str, Any]:
    """
    Docstring describing the function.

    Args:
        arg1: Description of arg1
        arg2: Description of arg2 (default: 10)

    Returns:
        {success, data: {...}, error}
    """
    try:
        with unreal.ScopedEditorTransaction("NodeToCode: main_function"):  # one undo reverts an edit
            value = arg1 * arg2
        return make_success_result({"result": value})
    except Exception as e:  # never a bare except
        log_error(f"main_function failed: {e}")
        return make_error_result(str(e))


result = main_function("x", 2)  # run-python returns `result` as data
```

## Enabling run-python over MCP

`run-python` is only registered when the per-user setting
**Allow MCP Python Execution** (`UN2CUserSettings::bAllowMcpPythonExecution`, read through
`UN2CUserSettings::IsMcpPythonExecutionAllowed()`) is on; it is off by default, needs an editor restart, and only the
user's own Saved/Config value counts (a project's committed config cannot turn it on, card 0423). The Python scripting
only profile without it serves no tool.
